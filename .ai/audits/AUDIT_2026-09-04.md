## Structured Findings

### [SEC-01]: Storage of Unsanitized Raw Payload Violating PII & Telemetry Governance Invariants
- **Severity:** P1 — Critical
- **Category:** Security
- **Location:** `benchmarks/server.py#L73-L74`, `benchmarks/server.py#L157`, `benchmarks/server.py#L298-L313`
- **Description:** PXOS core governance and privacy invariants state in `PROJECT_CONTEXT.md`: *"Telemetry: strictly anonymous, numeric metrics and categorical enums only. Anti-priorities: Unconsented or opaque data collection (strict privacy and opt-in standards). Safe ingestion: payload sanitization, range checks, and PII scrubbing before SQLite storage."* While `validate_and_sanitize_payload()` extracts and validates numerical metrics into the `sanitized` dictionary, line 157 assigns `"raw_payload": json.dumps(data)` and line 313 commits it directly into the SQLite database. Any arbitrary extra fields, personal author names, internal absolute file paths, or proprietary code accidentally included in incoming JSON payloads are persisted unscrubbed in the database.
- **Evidence:**
  ```python
  # benchmarks/server.py:157
  "raw_payload": json.dumps(data)

  # benchmarks/server.py:298-313
  INSERT INTO submissions (..., raw_payload) VALUES (..., ?)
  ```
- **Remediation:** Store `json.dumps(sanitized)` instead of `json.dumps(data)`, or explicitly whitelist only scrubbed fields before serializing `raw_payload`, guaranteeing that non-schema keys and sensitive payload fragments are discarded prior to database insertion.
- **Status:** Resolved (T-06)

### [PKG-01]: PyPI Package Missing CLI Helper Scripts and Offline Templates
- **Severity:** P1 — Critical
- **Category:** Architecture
- **Location:** `pyproject.toml#L49-L52`, `pxos/cli.py#L52-L64`, `pxos/cli.py#L210-L228`
- **Description:** `pyproject.toml` configures package discovery with `include = ["pxos*"]` and declares no package data. Consequently, when installed via PyPI (`pip install pxos`), the `scripts/` and `templates/` directories are completely omitted from the wheel in `site-packages`. When an end user runs `pxos benchmark` or `pxos monitor`, `pxos/cli.py` searches for `Path(__file__).resolve().parent.parent / "scripts/pxos-benchmark.py"`, which resolves to `site-packages/scripts/pxos-benchmark.py` (which does not exist), crashing with: `"scripts/pxos-benchmark.py not found in local installation."`. Furthermore, `pxos init` local template lookup fails, forcing an unauthenticated HTTP fetch to GitHub raw; in offline or air-gapped environments, project initialization fails completely.
- **Evidence:**
  ```python
  # pxos/cli.py:211-217
  script = Path(__file__).resolve().parent.parent / "scripts/pxos-benchmark.py"
  if script.exists():
      cmd = [sys.executable, str(script)] + sys.argv[2:]
      sys.exit(subprocess.call(cmd))
  else:
      err("scripts/pxos-benchmark.py not found in local installation.")
      sys.exit(1)
  ```
- **Remediation:** Include `templates/` and `scripts/` inside the `pxos` package namespace (or declare them in `[tool.setuptools.package-data]`), and update `pxos/cli.py` to resolve resources relative to `Path(__file__).resolve().parent`.
- **Status:** Resolved (T-06)

### [REL-01]: Unhandled SQLite Exceptions and Leaked Connections in Request Handlers
- **Severity:** P1 — Critical
- **Category:** Reliability
- **Location:** `benchmarks/server.py#L196-L233`, `benchmarks/server.py#L288-L317`
- **Description:** In `TelemetryRequestHandler`, database queries in `do_GET` (`/api/v1/stats`) and `do_POST` (`/api/v1/telemetry`) acquire `DB_LOCK` and open SQLite connections without enclosing `try...except sqlite3.Error` or `try...finally: conn.close()`. If `cur.execute` encounters a disk full condition, database lock timeout, or table corruption, `conn.close()` is never reached, leaking open file descriptors across threads until Python GC. Additionally, the unhandled exception propagates out of the handler, causing `ThreadingHTTPServer` to drop the socket without returning a structured JSON error response (`500 Internal Server Error`).
- **Evidence:**
  ```python
  # benchmarks/server.py:288-317
  with DB_LOCK:
      conn = sqlite3.connect(DB_PATH)
      cur = conn.cursor()
      cur.execute("""
          INSERT INTO submissions (...) VALUES (...)
      """, (...))
      row_id = cur.lastrowid
      conn.commit()
      conn.close()
  ```
- **Remediation:** Wrap all database operations in `try...finally: conn.close()` and catch `sqlite3.Error`, returning a standard JSON error response (`self.send_json(500, {"error": "Database error"})`).
- **Status:** Resolved (T-06)

### [SEC-02]: Unvalidated X-Forwarded-For Header Allowing IP Spoofing and Missing Ingestion Rate Limiting
- **Severity:** P2 — Major
- **Category:** Security
- **Location:** `benchmarks/server.py#L286`
- **Description:** `TelemetryRequestHandler.do_POST` trusts the `X-Forwarded-For` header unconditionally (`self.headers.get("X-Forwarded-For", self.client_address[0]).split(",")[0].strip()`). Any HTTP client can send an arbitrary `X-Forwarded-For: 1.1.1.1` header to spoof their IP address in the `submissions` audit log. Furthermore, there is no rate limiting or IP-based throttling on `POST /api/v1/telemetry`, allowing an attacker or runaway agent loop to spam 64 KB JSON payloads, bloating the database and degrading query performance.
- **Evidence:**
  ```python
  # benchmarks/server.py:286
  client_ip = self.headers.get("X-Forwarded-For", self.client_address[0]).split(",")[0].strip()
  ```
- **Remediation:** Only trust `X-Forwarded-For` when `self.client_address[0]` matches a configured list of trusted reverse proxies (e.g. `127.0.0.1`). Implement a lightweight in-memory rate limiter (e.g., sliding window or token bucket) restricting ingestion per IP to e.g. 10 requests per minute.
- **Status:** Resolved (T-06)

### [REL-02]: Unhandled Type Conversions Outside Exception Block in Telemetry Sanitizer
- **Severity:** P2 — Major
- **Category:** Reliability
- **Location:** `benchmarks/server.py#L151-L154`
- **Description:** In `validate_and_sanitize_payload`, the `try...except (ValueError, TypeError)` validation block terminates at line 128. However, lines 151-154 perform direct `int()` conversions on architectural fidelity fields (`invariants_violated_count`, `duplicate_utilities_introduced`, `adrs_consulted_count`, `new_adrs_registered`) outside of any `try` block. If an agent or client submits non-integer values (such as strings or malformed objects) for these fields, `int()` raises an unhandled `ValueError` at line 151, bypassing the validation response and causing an uncaught 500 error on the request thread.
- **Evidence:**
  ```python
  # benchmarks/server.py:127-128
      except (ValueError, TypeError) as e:
          return False, f"Type validation error in numeric telemetry: {e}", None
  ...
  # benchmarks/server.py:151-154
          "invariants_violated": int(arch.get("invariants_violated_count", 0)),
          "duplicate_utils": int(arch.get("duplicate_utilities_introduced", 0)),
          "adrs_consulted": int(arch.get("adrs_consulted_count", 0)),
          "new_adrs": int(arch.get("new_adrs_registered", 0)),
  ```
- **Remediation:** Move the `arch` integer conversions into the main `try...except (ValueError, TypeError)` block alongside the other numerical telemetry validations.
- **Status:** Resolved (T-06)

### [PERF-01]: Temporary File Disk Thrashing in Public Web Directory During Telemetry Aggregation
- **Severity:** P2 — Major
- **Category:** Performance & Memory
- **Location:** `benchmarks/aggregate_daily.py#L49-L56`
- **Description:** In `run_daily_aggregation()`, for every database submission, the script writes a temporary file `_tmp_{idx}.json` directly into `PUBLIC_DIR` (`/opt/pxos-telemetry/public`), calls `analyze.load_record_from_json()`, and immediately unlinks the file. This creates unnecessary disk I/O thrashing proportional to the number of records. More critically, because `PUBLIC_DIR` is served directly by web servers (e.g. Nginx), these transient JSON files containing raw unaggregated submission data are briefly exposed over HTTP to web crawlers or concurrent visitors.
- **Evidence:**
  ```python
  # benchmarks/aggregate_daily.py:49-56
  tmp_file = PUBLIC_DIR / f"_tmp_{idx}.json"
  with open(tmp_file, "w", encoding="utf-8") as f:
      json.dump(tmp_data, f)
  rec = analyze.load_record_from_json(tmp_file)
  if rec:
      records.append(rec)
  if tmp_file.exists():
      tmp_file.unlink()
  ```
- **Remediation:** Add `load_record_from_dict(data: dict)` in `benchmarks/analyze.py` so that `aggregate_daily.py` parses records directly in memory from decoded JSON dictionaries without touching disk storage.
- **Status:** Resolved (T-06)

### [REL-03]: Script Crash on Nested Branch Slashes in Worktree Spec Provisioning
- **Severity:** P2 — Major
- **Category:** Reliability
- **Location:** `scripts/pxos-task.sh#L39-L40`, `scripts/pxos-task.ps1#L55-L56`
- **Description:** When creating a worktree for branch names containing multiple slashes (e.g., `feat/telemetry/fix-wal` or `fix/auth/token-refresh`), `sed` / regex strips only the leading prefix (`feat/`), leaving `telemetry/fix-wal`. The resulting spec file path is set to `.ai/specs/SPEC-telemetry/fix-wal.md`. Because the intermediate subdirectory `.ai/specs/SPEC-telemetry/` does not exist, `touch` (in bash) or `Copy-Item` (in pwsh) crashes with `No such file or directory` or `DirectoryNotFoundException`, aborting the worktree provisioning workflow.
- **Evidence:**
  ```bash
  # scripts/pxos-task.sh:39-40
  SPEC_SUFFIX=$(echo "$BRANCH" | sed -E 's/^(feat|fix|chore|refactor)\///')
  SPEC_FILE=".ai/specs/SPEC-${SPEC_SUFFIX}.md"
  ```
  ```powershell
  # scripts/pxos-task.ps1:55-56
  $specSuffix = $Branch -replace '^(feat|fix|chore|refactor)/', ''
  $specFile = ".ai/specs/SPEC-$specSuffix.md"
  ```
- **Remediation:** Sanitize all remaining forward slashes in `$SPEC_SUFFIX` to hyphens (e.g., `SPEC_SUFFIX=$(echo "$BRANCH" | sed -E 's/^(feat|fix|chore|refactor)\///' | tr '/' '-')`) so that modular specs are always created as valid single-level filenames under `.ai/specs/`.
- **Status:** Resolved (T-06)

### [REL-04]: GitHub Release Step Tag Collision on Manual workflow_dispatch
- **Severity:** P3 — Minor
- **Category:** Architecture
- **Location:** `.github/workflows/release.yml#L7`, `.github/workflows/release.yml#L46-L48`
- **Description:** `.github/workflows/release.yml` triggers on both `push: tags: ['v*']` and `workflow_dispatch`. However, the GitHub Release step unconditionally uses `"${{ github.ref_name }}"` as the release tag name. When manually triggered via `workflow_dispatch` on a branch (e.g. `main`), `github.ref_name` resolves to `"main"`, causing `gh release create "main"` to attempt creating an invalid release tagged `"main"` on the default branch.
- **Evidence:**
  ```yaml
  # .github/workflows/release.yml:46-48
  gh release create "${{ github.ref_name }}" dist/* \
    --title "${{ github.ref_name }} — AI Indexability & Zero-Friction Distribution Engine" \
    --generate-notes
  ```
- **Remediation:** Gate the GitHub Release and PyPI publishing steps with `if: startsWith(github.ref, 'refs/tags/v')` or require a tag input parameter on `workflow_dispatch`.
- **Status:** Resolved (T-06)

### [REL-05]: Potential NoneType Iteration Crash in Benchmark Client on Null JSON Attributes
- **Severity:** P3 — Minor
- **Category:** Reliability
- **Location:** `scripts/pxos-benchmark.py#L109-L110`
- **Description:** In `scripts/pxos-benchmark.py`, list comprehensions for `identified_frictions` and `concrete_benefits` use `crit.get("identified_frictions", [])`. If a benchmark JSON file explicitly defines `"identified_frictions": null`, `crit.get()` returns `None` instead of `[]`. Iterating over `None` causes an uncaught `TypeError: 'NoneType' object is not iterable`.
- **Evidence:**
  ```python
  # scripts/pxos-benchmark.py:109-110
  "identified_frictions": [str(f)[:256] for f in crit.get("identified_frictions", [])][:5],
  "concrete_benefits": [str(b)[:256] for b in crit.get("concrete_benefits", [])][:5]
  ```
- **Remediation:** Use `crit.get("identified_frictions") or []` and verify the value is an iterable list or tuple before slicing.
- **Status:** Resolved (T-06)
