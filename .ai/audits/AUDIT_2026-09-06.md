## Structured Findings

### [PKG-02]: Critical Desynchronization of Bundled Templates in `pxos/templates/` (PyPI Drift)
- **Severity:** P1 — Critical
- **Category:** Architecture & Distribution
- **Location:** `pxos/templates/.ai/AI_BASE.md#L2`, `pxos/templates/.ai/PROJECT_CONTEXT.md#L2`, `pyproject.toml#L53-L54`
- **Description:** `pyproject.toml` bundles package data from `pxos/templates/` and `pxos/scripts/`. When an end-user installs PXOS via PyPI (`pip install pxos`) and executes `pxos init` or `pxos update`, templates are extracted from `pxos/templates/`. However, `pxos/templates/.ai/AI_BASE.md` is frozen on `v2.2.0` (144 lines), completely missing the `v2.4.0` Completion Honesty Protocol, No-Assumption Clause, and Mutation Lifecycle Checks. Additionally, `pxos/templates/.ai/PROJECT_CONTEXT.md` lacks the `Critical invariants` section. Downstream developers installing via PyPI receive obsolete governance rules without warning.
- **Evidence:**
  ```markdown
  # templates/.ai/AI_BASE.md (Root - 158 lines):
  <!-- pxos:version 2.4.0 -->
  - Completion Honesty Protocol, No-Assumption Clause present

  # pxos/templates/.ai/AI_BASE.md (Package Data - 144 lines):
  <!-- pxos:version 2.2.0 -->
  - Missing all v2.4.0 cognitive reliability rules
  ```
- **Remediation:** Synchronize `pxos/templates/` and `pxos/scripts/` with root sources immediately. Implement an automated parity test in `tests/test_audit_remediation.py` asserting content equality between `templates/` and `pxos/templates/`.
- **Status:** Resolved

### [PKG-03]: `generate-llms-txt.py --check` Failure & Tri-Fold Crawlability Drift
- **Severity:** P2 — Major
- **Category:** Reliability & AI Indexability
- **Location:** `scripts/generate-llms-txt.py#L120-L135`, `llms-full.txt`, `templates/site/public/llms-full.txt`, `pxos/templates/site/public/llms-full.txt`
- **Description:** Running `py scripts/generate-llms-txt.py --check` fails with exit code 1 (`Check Failed: llms-full.txt is missing or out of sync.`). The compiled `llms-full.txt` in the root repository was not re-generated when `AI_BASE.md` was upgraded to `v2.4.0`. Furthermore, `scripts/generate-llms-txt.py` only mirrors to `templates/site/public/` and ignores `pxos/templates/site/public/`, creating a three-way split where public web indexers, LLM scrapers, and PyPI installations receive divergent copies of the documentation.
- **Evidence:**
  ```bash
  $ py -3 scripts/generate-llms-txt.py --check
  Check Failed: llms-full.txt is missing or out of sync.
  ```
- **Remediation:** Update `scripts/generate-llms-txt.py` to mirror files to `pxos/templates/site/public/`. Re-generate `llms.txt` and `llms-full.txt` and ensure `--check` passes in CI.
- **Status:** Resolved

### [REL-06]: Absence of Automated CI Test Pipeline on Pull Requests and Pushes
- **Severity:** P2 — Major
- **Category:** Reliability & CI/CD
- **Location:** `.github/workflows/release.yml`, `.github/workflows/`
- **Description:** The repository only contains `.github/workflows/release.yml`, which triggers exclusively on version tags (`v*`). There is no continuous integration workflow (`test.yml` or `ci.yml`) that triggers on push or pull request to `main`. As a result, the automated unit test suite (`tests/test_audit_remediation.py`) and crawlability checks are never executed automatically. Regressions in telemetry validation, SQLite connection lifecycle, or packaging can be merged undetected.
- **Evidence:**
  `.github/workflows/` contains only `release.yml`. No push/pull_request triggers exist for testing.
- **Remediation:** Create `.github/workflows/test.yml` with a matrix build (Python 3.8 to 3.12 on ubuntu-latest and windows-latest) running `python -m unittest discover tests` and `python scripts/generate-llms-txt.py --check`.
- **Status:** Resolved

### [PERF-02]: Unbounded Memory Growth in Server In-Memory Rate Limiter (`IP_REQUEST_HISTORY`)
- **Severity:** P2 — Major
- **Category:** Performance & Memory
- **Location:** `benchmarks/server.py#L33`, `benchmarks/server.py#L40-L51`
- **Description:** `benchmarks/server.py` implements a sliding-window rate limiter using `IP_REQUEST_HISTORY: Dict[str, list]`. While the request timestamps for a given IP are pruned with `[t for t in history if now - t < RATE_LIMIT_WINDOW_SECS]`, the dictionary keys themselves are never deleted. When exposed to internet traffic or port scanning across hundreds of thousands of distinct IP addresses over weeks of uptime, `IP_REQUEST_HISTORY` will accumulate an unbounded number of empty or stale entries, causing a memory leak and risk of process OOM.
- **Evidence:**
  ```python
  # benchmarks/server.py:47-50
  if len(valid_history) >= MAX_REQUESTS_PER_WINDOW:
      IP_REQUEST_HISTORY[ip] = valid_history
      return True
  valid_history.append(now)
  IP_REQUEST_HISTORY[ip] = valid_history
  # Notice: No eviction when len(valid_history) == 0, and no max dictionary size cap
  ```
- **Remediation:** Implement periodic pruning in `is_rate_limited` (e.g. if an IP's valid history is empty, delete the key from `IP_REQUEST_HISTORY`), or enforce a maximum LRU/capacity cap (e.g., max 10,000 tracked IPs).
- **Status:** Resolved

### [PKG-04]: Missing Pre-Build Synchronization Hook in Packaging Pipeline
- **Severity:** P2 — Major
- **Category:** Architecture & Build Tooling
- **Location:** `.github/workflows/release.yml#L34-L37`, `pyproject.toml`
- **Description:** `.github/workflows/release.yml` executes `python -m build` directly. There is no automated pre-build hook or script to ensure that `pxos/templates` and `pxos/scripts` are synchronized with `templates/` and `scripts/` prior to wheel assembly. If a developer edits a template in `templates/` and tags a release, PyPI receives stale templates without failing the build.
- **Evidence:**
  ```yaml
  # release.yml:34-36
  - name: Build Source Distribution and Wheel
    run: |
      python -m build
  ```
- **Remediation:** Add a synchronization and validation step before `python -m build` in `release.yml`, or provide a `scripts/sync-package-data.py` script invoked during build or testing.
- **Status:** Resolved

### [REL-07]: Server Concurrency Resilience: SQLite Busy Timeout and Host Binding
- **Severity:** P3 — Minor
- **Category:** Reliability & Deployment
- **Location:** `benchmarks/server.py#L59`, `benchmarks/server.py#L269`, `benchmarks/server.py#L375`, `benchmarks/server.py#L420`
- **Description:** `benchmarks/server.py` opens `sqlite3.connect(DB_PATH)` without a custom `timeout` parameter or setting `PRAGMA busy_timeout = 5000`. Under concurrent write bursts, requests may fail immediately with `sqlite3.OperationalError: database is locked`. Furthermore, `run_server()` binds hardcoded to `127.0.0.1`, preventing containerized Docker deployments where `HOST="0.0.0.0"` is required via environment variable.
- **Evidence:**
  ```python
  # benchmarks/server.py:420
  server_address = ("127.0.0.1", PORT)
  ```
- **Remediation:** Support `HOST = os.environ.get("HOST", "127.0.0.1")`. Connect to SQLite using `sqlite3.connect(DB_PATH, timeout=30.0)` and execute `PRAGMA busy_timeout = 5000`.
- **Status:** Resolved
